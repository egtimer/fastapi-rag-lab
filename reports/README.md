# Reports

Each subdirectory is one committed benchmark run: the raw `benchmark.json` written by `tests/eval/run_benchmarks.py`, plus an `analysis.json` produced from it by `python -m fastapi_rag_lab.eval.analyze` (bootstrap 95% confidence intervals and paired comparisons between strategies). Numbers quoted in the top-level README should come from these files, so they can be checked and re-derived without re-running the benchmark. The analysis records the input file's sha256, the seed and the command used.

The judge runs `2026-10-30-judge-haiku-so-dev-50` and `2026-10-30-judge-sonnet-so-dev-50` were made on 2026-10-30 (see `started_at` in their `summary.json`) under the run ids `2026-10-31-judge-*-so-dev-50`, a mistyped date. The directories were renamed afterwards; `run_id` and `command` in their `summary.json` keep the ids as they were run. `2026-10-30-judge-agreement-so-dev-50/agreement.json` was regenerated with the renamed paths (same numbers).

## `git.dirty` in the provenance

Most runs here record `"dirty": true` next to their commit: every retrieval run except `2026-10-19-golden30-benchmark` (clean) and the April run (`2026-04-17-golden30-benchmark`, which predates the provenance block), including the two CI reference runs `ci-40306048985-*` made on a fresh checkout on the runner, and every judge run. The two judge item runs are clean. The flag comes from `git status --porcelain` (`src/fastapi_rag_lab/eval/provenance.py`), which also lists untracked files, and `reports/` is not gitignored, so a run directory that exists but is not yet committed is enough to set it. The flag cannot tell that apart from modified code, and what was uncommitted at the time was not recorded, so the commit in a report identifies the code only up to that. These runs were not repeated on a clean tree. What each report does pin independently of the flag:

- Retrieval runs: the dataset sha256, the corpus commit and manifest sha256, the Qdrant server version and point count, the Ollama version and embedding model digest, the reranker revision and the package versions. The weekly retrieval eval re-runs the benchmarks on a fresh checkout and compares `hybrid_k5` with the committed CI reference by paired bootstrap.
- Judge runs: the sha256 of the judge system prompt actually sent (`judge_prompt_sha256`, or the prompt text itself in the 2026-10-30 runs). It matches `prompt.sha256` in the item runs for every run (v1 `9aadfd71…`, v2 `1af9acf8…`), and from 2026-11-10 on each judge run also records the sha256 of the items it judged (`items_sha256`).
